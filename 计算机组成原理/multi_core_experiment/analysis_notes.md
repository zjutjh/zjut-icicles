# 实验数据整理说明

## 1. Windows 数据处理原则
Windows 主结果文件中，1线程数据波动很大；补跑文件中 1线程第1次仍明显低于其余多次结果。为避免用明显异常值直接拉高加速比，本次整理采用两套口径：

- **运行时间分析口径**：
  - 1线程运行时间采用 `results_windows_low_threads.csv` 中去掉第1次后的 4 次平均值：
    - (18.728719 + 19.853539 + 22.072320 + 19.330404) / 4
    - = **19.996246 s**
  - 2线程、4线程采用 `results_windows_low_threads.csv` 的 5 次平均值
  - 8线程及以上采用 `results_windows.csv` 的 3 次平均值
- **加速比与并行效率展示口径**：
  - 为避免出现“2线程比1线程更快很多但分母异常偏大”的误导，也避免直接使用异常慢的 1线程均值，采用已观测到的**最佳单线程基准** `6.970134 s` 作为 speedup reference。
  - 该口径更接近“理想单线程状态下的性能对比”，同时需要在报告中明确说明。

## 4. 可直接写入分析的现象
- Windows 平台在 1→16 线程区间运行时间显著下降；16 线程之后仍有收益，但边际收益减弱。
- Windows 平台在 24→32→48→64 线程区间仍有小幅下降，说明该平台在此程序上还能从更多逻辑线程中获得部分收益，但提升已经明显进入平台期。
- Linux 平台在三个矩阵规模上都表现出：2线程收益最明显，4线程进一步改善有限，8线程基本进入平台期。
- Linux 在 1400 规模下 8线程略慢于 4线程，说明线程数继续增加后，调度/访存/资源竞争开销可能抵消了并行收益。
- Linux 平台随矩阵规模增大，2线程效果一直较好，但 4线程和 8线程并未随规模明显拉开差距，说明服务器端可能存在更强的资源限制。
